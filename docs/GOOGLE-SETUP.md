# 網站原生表單連接 Google 試算表

同事在網站的原生表單完成許願、贊同、盤點、入庫與新增飲料。Apps Script 將資料寫進私人試算表，網站收到儲存回條後顯示成功，不用開啟 Google 表單。

持有網站連結的人都能查看倉庫、登記數量；登記人／贊同姓名由填寫者自行提供，不是登入驗證。原始試算表保持「受限制」，不用發布為 CSV，也不用開放任何人編輯。

## 已有 Google 部署：更新原生表單

已執行過 `setupOnce`、網站也已接上 `/exec` 的人，使用以下步驟即可：

1. 開啟 [最新版 Code.gs](https://github.com/reytai-hldwn/pantry/blob/main/google-apps-script/Code.gs)，複製完整程式。
2. 開啟原本的 [Apps Script 專案](https://script.google.com/)，用完整程式取代原 `Code.gs`，按儲存。
3. 右上角 **部署 → 管理部署 → 選取原網頁應用程式 → 鉛筆「編輯」 → 版本選「新版本」 → 部署**。執行身分維持「自己」，存取者維持「任何人」。若 Google 要求授權，由專案擁有人完成。
4. 回到 [正式網站](https://reytai-hldwn.github.io/pantry/) 重新整理，即可使用原生表單。若仍開啟 Google 表單，確認第 3 步已發布新版本，並重新整理網站。

**此次不必重跑 `setupOnce`，不用重建試算表，也不用新增部署網址。** 沿用原 `/exec` 及 GitHub 的 `GOOGLE_SCRIPT_URL`。第一筆網站送出時會自動新增 `WebsiteRequests` 分頁；既有品項、數量、願望與歷史不會清除。

只按「儲存」不會更新正在使用的 `/exec`，必須完成「管理部署 → 新版本」。目前工具無法代替擁有人進入 Google 帳號完成這個步驟。

## 第一次設定 Google

1. 在 [Apps Script](https://script.google.com/) 新增專案，完整貼入 [Code.gs](../google-apps-script/Code.gs)。日常使用不需要填 `ADMIN_EMAILS`。
2. 選取 `setupOnce` 執行，由擁有人同意 Google 試算表／表單權限。執行紀錄會提供私人試算表入口，也可在同一 Google 帳號的雲端硬碟尋找新建立的檔案。
3. **部署 → 新增部署 → 網頁應用程式**，執行身分選「自己」，存取者選「任何人」，取得結尾 `/exec` 的網址。
4. 依 [GitHub Pages 上線步驟](GO-LIVE.md) 設定 `GOOGLE_SCRIPT_URL` 並發布網站。

初始化仍會保留五張 Google 表單與原始回應，供既有流程相容使用。新版網站直接使用 Apps Script 原生送出，不依賴同事填寫或發布這五張 Google 表單。若還要使用舊表單，另在各表單設定允許「任何人」、不收 Email、不限一人一次；組織政策可能需要 Workspace 管理員調整。

初始化包含 32 款供應品項與 8 款歷史品項，每箱預設 24，實際數量先顯示待盤點。歷史品項的 `active = FALSE`，不出現在盤點及入庫選單。恢復供應可在私人 `Catalog` 將同一列改回 `TRUE`，保留原 ID 與紀錄。

## 試算表分頁與保存方式

| 分頁 | 用途 |
| --- | --- |
| `Catalog` | 品項、分類、包裝、每箱數量、門檻與啟用狀態 |
| `Warehouse`、`Archive` | 目前及歷史品項的數量檢視，重新整理不刪除來源紀錄 |
| `History` | 盤點／到貨、登記人、時間與採計結果 |
| `WishReview` | 匿名願望、飲料／零食分類、採購狀態 |
| `WishVotes` | 贊同姓名、瀏覽器識別碼與採計結果 |
| `ProductIntake` | 快速新增飲料的登記人與採計紀錄，不產生虛構庫存 |
| `WebsiteRequests` | 原生送出的識別碼、待確認／接受／拒絕狀態與重試資料；首次送出自動建立 |
| `Setup` 與表單回應分頁 | 既有 Google 表單入口及原始回應 |

請保留來源紀錄與 `WebsiteRequests`，不要刪列後重試。舊 Google 表單觸發器會繼續採計；新飲料透過網站新增後，原生盤點及入庫選單讀取同一個 `Catalog`。

## 網站填寫規則

- **許願**：必選飲料或零食、必填名稱，不收姓名；連結及備註選填。
- **贊同**：必填姓名，儲存後顯示於贊同名單。同一瀏覽器對同一願望一票；清除瀏覽器資料或換裝置會產生不同識別碼。舊票未留姓名仍保留票數。
- **盤點**：必填登記人，至少填一個品項；留白不改動，0 是有效盤點。
- **到貨**：必填登記人，整箱或零散可擇一，也可同填加總；合計須大於 0。每箱預設 24，採用 `Catalog` 的實際設定。
- **新增飲料**：必填品名、分類、包裝與登記人；不用先上傳圖片。送出後以示意圖上架、每箱預設 24、數量為待盤點。同名品項（忽略大小寫、全半形與頭尾空白）不重複建立；日後補圖沿用同一 ID。

送出中會顯示儲存狀態並停用重複點擊。等待過久時保留原內容再送，沿用同一識別碼；系統只寫入一次。若已儲存但更新畫面失敗，網站會告知重新整理，不會要求新增第二筆。

## 資料介面

- `GET /exec?action=public`：品項、願望、贊同姓名與原生送出能力 `websiteEntry: { version: 1 }`，不含庫存與異動紀錄。
- `GET /exec?action=warehouse`：庫存、最近盤點與異動／登記人，不含管理帳號或瀏覽器識別碼。
- `POST /exec`：只接受 `wish`、`vote`、`stocktake`、`arrival`、`product` 五種指定操作。伺服器驗證品項、數量、必填資料及重複請求，不接受整份資料覆寫。
- `GET /exec?action=receipt&requestId=…`：只回傳該筆儲存狀態與必要結果，不公開原始輸入、登記人或重試資料。

讀取支援經過驗證的 JSONP `callback`。POST 使用隱藏的 HTML 表單與傳輸 iframe，網站畫面仍是原生表單；只有讀到接受回條才視為成功，iframe 載入不算儲存確認。`updatedAt` 是同步時間，不代表追蹤日常取用。

舊版 Apps Script 沒有 `websiteEntry.version=1` 時，網站暫時沿用舊 Google 表單流程。更新既有部署後，網站會自動切換原生介面。

## 更新後確認

桌機與手機的五種原生操作、數量驗證、重試及中途失敗恢復已通過模擬測試，未寫入正式試算表。擁有人更新部署後，再確認以下真實同步：

1. 用未登入 Google 的手機開網站，表單能留在網站填寫，不跳新分頁。
2. 登記一筆實際盤點／到貨，確認網站與 `History` 的登記人、時間、數量一致；另一部手機重新整理也能看到。
3. 匿名許願，填姓名贊同，確認名單與票數同步；同瀏覽器重送不加票。
4. 新增實際需要的飲料後，確認它出現在冰箱、盤點及入庫選單；初始為待盤點，舊資料保持原值。

若沒有更新，先確認已發布「新版本」，再查看 Apps Script「執行項目」及 `WebsiteRequests` 狀態。`pending` 表示結果仍待確認，保留原內容重試即可；不要刪除舊回應或手動補一筆相同到貨。

## 匯入先前的私人盤點

這是獨立的私人匯入步驟，原生表單升級不會自行匯入任何私人數量。先完成 `setupOnce`，在自己的 Apps Script 的 `ADMIN_EMAILS` 加入擁有人 Google 帳號並執行 `setupConfig`。將已準備好的私人 `GoogleImport.gs` 新增為同專案的指令碼檔，執行 `importReportedStocktake`。檔案自帶已確認的原盤點時間與數量，重跑同批次不重複增加，也不把匯入時間當成盤點時間。完成後執行 `refreshWarehouse`。

私人盤點檔與 Google 帳號保留在私人位置，不提交至公開 GitHub。
